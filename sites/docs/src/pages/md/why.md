# 为什么选它 · 和其他组件库的对比

一句话：**admin-ui 不是又一套通用组件库，它专门做数据密集型的管理后台**——表格、视图、看板、记录详情、权限和协作这些自己写要几个月的部分，直接给成品；通用的按钮、输入框也有，但不是重点。

下面的对比尽量老实：优势、区别、短板都写。别家的情况以它们官网为准，标「未核实」的是我们没有逐条验证的印象。

## 它适合谁

- 你在做 **CRM、工单、运营后台、内部工具、SaaS 的管理端**：页面以列表、记录、表单、看板为主，用户每天要在里面工作几个小时。
- 你想要 **飞书多维表格 / Airtable 那一类的体验**（格内编辑、视图、分组、看板、甘特），但不想为数据表格单独买商业授权。
- 你的团队（或你的 AI）需要 **一套定死的规范**：一种下拉、一种日期、一种出错样式，页面先选模板再写，审计命令能查出漂移。
- 你的界面以 **中文** 为主。

不太适合：营销官网、内容站、需要高度定制品牌视觉的 C 端产品、Vue / Angular 项目、需要多语言界面的产品（见下面「短板」）。

> 别家的细节（例如 MUI X 哪些功能在付费档、各家多语言数量）会随版本变化，选型前请以各自官网为准；表里「没有」指官方包里没有现成组件，不代表做不到。

**和 shadcn/ui 的关系**：admin-ui 的 Button / Input / Checkbox / Choice / FormDialog 借鉴了 shadcn/ui 的组合方式（同样基于 Radix），许可见包里的 THIRD-PARTY.md。区别是 admin-ui 是一个**包**而不是复制的源码：你得到的是统一规范和后续升级，代价是不能随手改组件内部样式（审计会拦 `.aui-*` 覆盖，缺什么回流到库里）。

**和 Ant Design Pro / Refine 的关系**：它们解决「后台怎么搭」——路由、布局、CRUD 数据流。admin-ui 解决「后台里的每一块长什么样、怎么交互」，数据流交给你自己的 adapter。Refine 理论上可以把 admin-ui 当 UI 层用（未验证，没有现成集成）。

## 短板（选之前请看）

1. **很新，API 变得快。** 1.0 在 2026-09-16，8.0 在 2026-10-08——三周里 8 个大版本。8.0 是一次「删旧不留兼容层」的大清理，之后计划放缓，但目前还没有长期支持承诺。好的一面：有迁移表和 `admin-ui-audit` 自动找出要改的地方。
2. **只有中文。** 组件里的文字（「请选择」「更多」「加载比较慢…」）是写死的中文，日期默认按 Asia/Shanghai 时区显示；还没有 locale 机制。要做英文界面，现在需要等库加上 i18n。
3. **只支持 React 19。** 不支持 React 18，不支持 Vue / Angular / Svelte。
4. **还没发布到公共 npm。** 目前从 Git 标签或 `npm pack` 的 tarball 安装。
5. **只有一种外观。** 规范是定死的（这是优点也是限制）：能换色卡和品牌色，但不能换成另一套设计语言；没有 Figma 组件库；不支持从右到左（RTL）布局。
6. **SSR 只做了基本保证。** 组件都是客户端组件（`"use client"`），Next.js 可以用，但没有官方示例工程，也没有服务端渲染的视觉回归测试。
7. **无障碍做了但没有第三方审计。** 键盘操作、焦点管理、aria、对比度都按规则写了，并有 48 个浏览器测试脚本覆盖，但没有做过正式的 WCAG 审计。
8. **生态小。** 没有第三方主题、插件和社区问答；遇到问题主要靠文档和源码。
9. **开发工具链要求新。** 包声明 Node ≥ 26，构建用 TypeScript 7。

## 一张表帮你选

| 你的情况 | 建议 |
|---|---|
| 中文管理后台，表格 / 看板 / 记录详情是重点 | admin-ui |
| 需要多语言、全球用户 | Ant Design、MUI、Mantine |
| 想要源码完全在自己手里、愿意自己拼 | shadcn/ui |
| Vue 项目 | TDesign、Arco（Vue 版）、Element Plus |
| 只要一个强大的数据表格，其余自己做 | MUI X Data Grid、AG Grid、TanStack Table |
| 想要现成的 CRUD 框架，UI 随便 | Refine、Ant Design Pro |
